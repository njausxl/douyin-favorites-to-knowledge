为什么采集要用浏览器而不是 API？ 抖音收藏夹接口需要登录态且带签名，直接在服务端请求会被拦。用 Playwright 起一个真实浏览器复用你已登录的会话，是唯一稳定的路子——代价是首次要扫码登录。

02单条收藏的分流决策

把富化层那一个菱形展开，就是单条收藏从进入系统到落盘的完整路径。

图 2 · 判定条件只有一条：item.images 是否非空
为什么必须分流？ 抖音给图文帖也填了 play_url，但那个地址指向的是背景音乐 MP3，不是视频流。如果不分流，这条会被当成普通视频送进语音识别，结果是把 BGM「听」成一段幻觉文本，状态却标成成功。你库里曾经出现的 🎼嗯。。🎼的都荡。The number you dialed is not available... 就是这么来的。
分流的真正意义是把劣质信号拦在门外——宁可走读图，也不让背景音乐污染笔记。

另外还有个兜底规则：sync 落盘前会再筛一道，failed / unavailable / too_large / budget_exceeded 这四种状态的条目会被从本轮剔除，避免每次同步都无谓重试同一批失败项。

05四条设计约束

整个架构是围绕四个踩过的坑长出来的：

  • 接口靠浏览器，不靠 API —— 收藏夹接口需要登录态和签名，服务端直连会被拦，所以必须复用本机浏览器会话。
  • 图片和声音走两条独立通道 —— 因为图文帖的 play_url 是背景音乐，混着走会产出幻觉文本。
  • ocr 字段不参与防重哈希 —— 哈希在挂载 OCR 之前算好，换视觉模型重跑不会撞「条目已变更」报错。
  • 账本管去重、Markdown 管阅读 —— 双写各司其职，账本让你下次同步时自动跳过已处理项。
